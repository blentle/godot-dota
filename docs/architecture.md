# 系统架构 · 决策基线 v0.1

## 产品边界

这是使用 Godot 重新实现 6.83d 的独立游戏。Godot 不直接执行 Warcraft III 的地图脚本和引擎行为；地图规则、技能、寻路、动画和 UI 均须转译并校验。平台最终启动本项目导出的游戏可执行文件。

先交付游戏：离线训练 → 代表性英雄与对战系统 → 全内容 → 网络对战验证。随后交付平台。网络权威边界从第一天保留，防止离线玩法写死到 UI 后再返工。

## 部署组成

游戏客户端与启动器均交付 Windows、macOS、Linux 版本；Linux 桌面客户端与 Linux 无界面对战服务器是不同的运行角色。三平台共用规则、协议和资源包，可在同一房间混合匹配。详见 platforms.md。

| 组成 | 技术选择 | 职责 |
|---|---|---|
| 游戏客户端 | Godot 4.7.2、GDScript、3D + Control HUD | 输入、渲染、音频、客户端插值、本地训练 |
| 对战进程 | 同一 Godot 工程 headless 导出 | 权威规则、10 人连接、视野过滤、战果 |
| 平台启动器 | 暂定 Godot 独立工程 | 登录、房间、更新校验、启动/监测游戏子进程 |
| 平台 API | 暂定 Go 模块化单体 | 账号、房间、匹配、启动票据、对战分配 |
| 数据库 | PostgreSQL | 账号、比赛、惩罚、战果、版本目录 |
| 临时状态 | Redis | 在线状态、队列、票据、短租约；不用作战果唯一存储 |
| 进程分配器 | Linux 本机进程管理，后续扩展多个节点 | 分配端口、启动/回收对战进程、健康检查 |
| 资源分发 | 对象存储 + HTTPS | 签名版本清单、分块更新、内容哈希 |

首期一台 Linux 主机部署 API、数据库、Redis 和多个对战进程。数据卷独立备份，API 走 HTTPS/WSS，对战 UDP 端口段按部署配置开放。最初不引入 Kubernetes；并发容量必须经 10 人战斗压测后决定，不能提前承诺单机房间数。

## 游戏内部边界

- `simulation`：固定 tick 世界、实体 ID、命令队列、属性、伤害、状态、计时、死亡复活、经济、胜负。初定 30 Hz，通过实测调整。
- `abilities`：施法前摇/后摇、目标类型、消耗、冷却、打断、投射物、范围效果、修饰器。复杂英雄允许专用逻辑，不强行只靠 JSON 拼技能。
- `world`：三路、河道、高低地、树木、野区、建筑、刷兵、野怪、商店、符点、Roshan、视野和战争迷雾。
- `presentation`：模型、骨骼动画、特效、音效、相机、HUD。只能读取世界状态，不能直接扣血、加钱或确认命中。
- `input`：右键、攻击移动、停止、保持、编队、选择与指令队列；输出结构化命令。
- `transport`：本地训练适配器与 ENet 网络适配器共用命令契约。本地训练仍通过规则层执行。
- `content`：固定版本的英雄、技能、物品、单位、商店、地图和本地化数据；整包由哈希标识。

权威进程可持有 Godot 场景，但模拟层避免依赖渲染、帧率和 UI。寻路/浮点实现不承诺跨机器确定性，因此不采用要求所有玩家完全同步模拟的 P2P 锁步方案。

## 网络原则

客户端发送意图；服务器校验控制权、技能目标、距离、视野、资源和指令速率。可靠通道传命令、阶段变更与关键事件；快照按序发送，旧包可丢弃。视觉移动允许预测，命中、资源消耗和死亡以服务器为准。

服务器只发送玩家可见的敌方信息；隐藏单位不进入客户端快照。重连采用新的限时票据恢复原席位，先加载完整快照再接收增量。命令包含单调序号，去重且有有界缓存。

回放先采用权威快照 + 事件日志，记录引擎版本、规则包哈希和随机种子；仅记录输入不足以保证跨平台复现。

## 平台到游戏的完整链路

1. 用户注册/登录平台，取得平台会话。
2. 选择大厅中的房间，选择 6.83d，点击开始；启动器先核对本地可执行文件与资源版本。
3. 平台按规则版本、地区和模式将玩家纳入队列。房间默认为匹配大厅，最终比赛严格分配 10 个唯一账号、每队 5 人；开黑组队和私人自定义房间另设队列策略。
4. 原子预留 10 个席位并发出 ready check；超时者移出，其余玩家保留原队列优先级。
5. 全员确认后分配服务器。服务器加载正确内容包并报告 ready；失败则释放席位/资源并恢复队列。
6. 平台分别签发绑定账号、比赛、席位和包哈希的单次短期启动票据。
7. 启动器用参数数组启动受管理的本地游戏路径，票据经受限 IPC 传递；不得拼接 shell 命令，不把平台长期令牌放入命令行。
8. 游戏兑换入场票据，连接对战服务器；装载地图和英雄资源并报告 load complete。
9. 服务器确认 10 个席位完成装载后进入选人/开局倒计时。客户端发 start 无法越过屏障。
10. 对战结束由服务器提交带唯一比赛 ID 的结果，平台幂等写入，启动器显示结算。游戏异常退出可在重连窗口内返回原局。

实际时限、选人模式和逃跑惩罚留在配置中，先用 All Pick 完成闭环，再扩充其他原版模式。

## 失败处理

队列与席位使用事务/租约，重复点击开始不会重复入队。取消与匹配同时发生时由原子状态迁移决定唯一结果。服务器启动失败、客户端启动失败、资源不一致、装载超时分别进入可观察状态，不能留在“匹配中”。

服务器崩溃首期标记比赛中断并退回大厅，不假装支持无损热迁移。结束回调重试不重复结算。平台断连不立刻终止已开始的比赛；对战完成后缓存结果等待平台恢复。

## 测试与观测

规则用无界面场景测试，记录每个 tick 的断言；英雄通过脚本化对局校验；HUD 固定场景截图比对；网络用延迟、丢包、断线、重复命令验证。平台使用 10 个独立测试身份跑闭环，模拟客户端必须明确标记。

日志关联 match_id、用户匿名 ID、进程 ID、规则哈希，不记录密码/票据。采集 tick 耗时、带宽、快照大小、装载耗时、队列等待时间、崩溃率。目标性能预算在首个完整战斗场景中建立。
